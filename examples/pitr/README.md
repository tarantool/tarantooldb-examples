# Резервное копирование и восстановление на момент времени (PITR)

В этом руководстве показано, как выполнить резервное копирование кластера Tarantool DB
и восстановить его данные на заданный момент времени (point-in-time recovery, PITR)
с помощью утилиты [tt CLI](https://www.tarantool.io/docs/tdb/ru/3_x/install_and_upgrade/install_tt).

Резервное копирование и восстановление является кластерной операцией. Утилита `tt` выполняет
её на узлах Tarantool и на отдельном хосте-менеджере, а файлы между ними переносит оркестратор.
В примере роль оркестратора выполняют скрипты `scripts/backup.sh` и `scripts/restore.sh`,
которые запускаются целями `make`.

Восстановление на момент времени выполняется по точкам восстановления (recovery points) — меткам
в WAL с отметкой времени. Их создаёт роль `roles.recovery-point-manager`, включённая на роутере.

## Запуск стенда

Для успешного запуска должны быть свободны следующие порты:

* 2379
* 3301–3307

Перейдите в директорию примера `pitr`:

```shell
cd examples/pitr
```

Запустите стенд:

```shell
make start
```

Команда последовательно выполняет следующие шаги:
1. Запускает централизованное хранилище конфигурации — кластер etcd;
2. Загружает конфигурацию кластера в централизованное хранилище;
3. Запускает кластер Tarantool DB. Контейнер `init_host` в его составе загружает
   миграции в кластер и выполняет их.

Запущенный стенд состоит из:

* кластера Tarantool DB:
  * роутера `router-1` (порт `3301`);
  * двух наборов реплик по три хранилища в каждом:
    * `storage-1`: мастер-узел `storage-1-msk` (порт `3302`), реплики `storage-1-spb` (порт `3303`) и `storage-1-brn` (порт `3304`);
    * `storage-2`: мастер-узел `storage-2-msk` (порт `3305`), реплики `storage-2-spb` (порт `3306`) и `storage-2-brn` (порт `3307`);
  * контейнера `manager` (хост-менеджера резервного копирования);
* кластера etcd из 3 узлов.

После запуска должны работать все контейнеры, кроме [init_host](../up_with_docker_compose/README.md#контейнер-init_host).

При запуске миграция создаёт шардированный спейс `customers` с полями `id`, `bucket_id`,
`name`, `surname` и `age`.

На роутере включена технологическая роль `roles.recovery-point-manager`, которая каждые 30 секунд
автоматически создаёт кластерную точку восстановления на всех мастер-узлах хранилищ.
Подробнее о роли и точках восстановления можно узнать в разделе
[Как устроено резервное копирование и восстановление](#как-устроено-резервное-копирование-и-восстановление).

## Используемые файлы

В руководстве используются следующие файлы примера `pitr`:

* `cluster/` — директория c файлами для запуска кластера Tarantool DB:
  * `config.yml` — конфигурация и топология кластера, в том числе технологическая роль
    `roles.recovery-point-manager` на роутере;
  * `docker-compose.yml` — описание узлов кластера Tarantool DB и контейнера `manager`;
  * `migrations/scenario` — директория, содержащая файлы с описанием миграций;
* `tools/docker-compose.yml` — описание кластера etcd из 3 узлов, который хранит конфигурацию кластера;
* `scripts/` — директория со скриптами-оркестраторами:
  * `backup.sh` — полное и инкрементальное резервное копирование;
  * `restore.sh` — восстановление на момент времени;
* `Makefile` — цели для запуска и остановки стенда, резервного копирования и восстановления.

## Как устроено резервное копирование и восстановление

Утилита `tt` выполняет резервное копирование и восстановление на двух уровнях:

* на **узле Tarantool** утилита создаёт локальный архив данных командой `tt backup start`,
  завершает резервное копирование с помощью команды `tt backup finalize`, а при восстановлении подготавливает
  каталог данных, используя `tt restore apply`;
* на **хост-менеджере** (отдельной машине с `tt`) `tt` строит план создания резервной копии с помощью команды
  `tt backup plan`, собирает манифест и загружает архивы в хранилище командой
  `tt backup upload`, а при восстановлении скачивает цепочку архивов и строит план восстановления
  командой `tt restore plan`.

Файлы между узлами и менеджером переносит **оркестратор** — внешняя система, например, ATE, скрипты
или CI/CD. В примере эту роль выполняют скрипты из директории `scripts/`.

В примере файлы размещены так:

* **резервные копии** — в хранилище `/backup/storage` (именованный том `backup`), на
  которое указывает флаг `--backup-storage`. С хранилищем работает только менеджер;
* **локальные архивы** — промежуточные файлы на мастер-узлах, в каталоге
  `/backup/archives` (тот же том `backup`). Том смонтирован и в `manager`, и в
  мастер-узлы хранилищ, поэтому менеджер видит архивы напрямую и переносить их
  не нужно;
* **данные экземпляров** — снимки данных и WAL Tarantool, в именованных томах `*-data`,
  смонтированных в `manager` под путями `/data/<экземпляр>`.

> [!NOTE]
> Общие тома используются здесь для упрощения примера. В промышленной эксплуатации узлы и менеджер — это отдельные
> машины, и локальные архивы между ними переносятся по SSH, а данные экземпляров
> находятся на самих узлах. Точно так же `--backup-storage` указывает здесь на файловое
> хранилище (`file:///backup/storage`), чтобы не поднимать отдельный сервис. В промышленной эксплуатации
> резервные копии обычно хранят в S3-совместимом объектном хранилище, которое `tt` тоже
> поддерживает в одном из вариантов ниже:
> - короткая форма `s3://<bucket>/<prefix>` с учётными данными из переменных
> окружения `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY`;
> - полная форма `@config.yaml`
> с полями `type`, `endpoint`, `region`, `bucket`, `prefix`, `access_key_id` и
> `secret_access_key` для пользовательского адреса обработки запросов и региона.

В примере выполняется два резервных копирования одной цепочки — сначала полное, а затем инкрементальное.
Восстановление выполняется на момент времени точки восстановления `before-incr`.

## Запись данных

Чтобы начать работу в интерактивной консоли Tarantool, подключитесь к роутеру
(порт `3301`) с помощью команды `tt connect`:

```shell
tt connect admin:secret-cluster-cookie@localhost:3301
```

Теперь запишите данные в спейс `customers`. В добавленных кортежах в поле `bucket_id` задано значение `box.NULL`. Это означает, что идентификатор сегмента (`bucket_id`) вычисляется автоматически:

```lua
crud.insert_many('customers', {
    {1, box.NULL, 'Elizabeth', 'Bagnall', 12},
    {2, box.NULL, 'Mary', 'Bowman', 46},
    {3, box.NULL, 'David', 'Bradley', 33},
    {1001, box.NULL, 'William', 'Bridgens', 81},
    {1002, box.NULL, 'Jack', 'Brown', 35},
    {1003, box.NULL, 'William', 'Long', 25},
})
```

Для выхода из консоли нажмите `CTRL+D` или введите команду `\quit`.

## Полное резервное копирование

Технологическая роль `roles.recovery-point-manager` автоматически создает точки восстановления,
поэтому перед полным резервным копированием ничего не требуется создавать вручную.

Выполните полное резервное копирование:

```shell
make backup-full
```

Скрипт `scripts/backup.sh`, запущенный этой командой, выполняет последовательно шаги ниже:
1. `tt backup-id` — получение идентификатора резервного копирования.
2. `tt backup plan` — построение плана резервного копирования.
3. `tt backup start` — создание резервной копии для каждого мастер-узла.
4. `tt backup upload` — загрузка архивов.
5. `tt backup finalize` — завершение процесса резервного копирования.

Каждый шаг скрипт выводит в консоль. Узнать больше: [Что выполняют скрипты-оркестраторы](#что-выполняют-скрипты-оркестраторы).

## Инкрементальное резервное копирование

Подключитесь повторно к узлу роутера:

```shell
tt connect admin:secret-cluster-cookie@localhost:3301
```

Добавьте новые кортежи в спейс `customers`:

```lua
crud.insert_many('customers', {
    {4, box.NULL, 'Alice', 'Anderson', 28},
    {5, box.NULL, 'Robert', 'Campbell', 41},
    {1004, box.NULL, 'Sarah', 'Mitchell', 33},
    {1005, box.NULL, 'James', 'Carter', 55},
})
```

Перед инкрементальным резервным копированием создайте точку восстановления с меткой `before-incr`.
Для этого подключитесь повторно к экземпляру роутера  (порт `3301`):

```shell
tt connect admin:secret-cluster-cookie@localhost:3301
```

Запишите метку на мастер-узел каждого набора реплик:

```lua
vshard.router.create_cluster_recovery_point('before-incr')
```

В ответе команда возвращает по метке на каждый набор реплик с полем `timestamp` — временем
в секундах с дробной частью. Для восстановления нужна целая часть значения `timestamp`. Например, в метке
`1790799106.5178132` используется значение `1790799106`. Значения у наборов реплик почти совпадают, так что
подойдёт любое.

Выполните инкрементальное резервное копирование:

```shell
make backup-incremental
```

## Повреждение данных

Имитировать потерю данных можно, очистив спейс с данными на роутере. Для этого подключитесь к узлу роутера
(порт `3301`):

```shell
tt connect admin:secret-cluster-cookie@localhost:3301
```

Теперь очистите спейс `customers` на роутере, используя модуль `crud`:

```lua
crud.truncate('customers')
```

## Восстановление на момент времени

Восстановите данные к созданной ранее точке `before-incr`, то есть к моменту, когда были записаны обе
порции данных. Передайте в переменной `TARGET_TIME` целую часть поля `timestamp` этой
точки. В примере команды ниже вместо `1790799106` подставьте целую часть `timestamp`, полученную при создании точки `before-incr` (см. раздел [Инкрементальное резервное копирование](#инкрементальное-резервное-копирование)):

```shell
make restore TARGET_TIME='1790799106'
```

Скрипт `scripts/restore.sh`, запущенный этой командой, выполняет последовательно шаги ниже:
1. `tt restore plan` — построение плана восстановления.
2. Остановка узлов хранилища.
3. `tt restore apply` — подготовка каталогов данных на каждом мастер-узле.
4. Очистка каталогов экземпляров реплик.
5. Запуск хранилища.

Восстанавливаются только мастер-узлы хранилищ — на те же экземпляры, на которых была создана
резервная копия. Реплики не восстанавливаются из резервного копирования: их каталоги данных очищаются, и при старте
они заново догоняют мастер-узел. Роутер не хранит данные и запускается с пустого состояния, при этом
он входит в резервное копирование (см. раздел [«backup.sh: резервное копирование»](#backupsh-резервное-копирование)).

Подменять идентификаторы экземпляров (`--patch-uuid`) не нужно. Мастер-экземпляр восстанавливается
на себя, поэтому значение `instance_uuid` в архиве уже совпадает с текущим. Параметр `--patch-uuid` требуется только
при переносе резервной копии на другой узел — например, при поднятии потерянного узла заново
как нового.

После восстановления подключитесь к роутеру (порт `3301`) для проверки данных:

```shell
tt connect admin:secret-cluster-cookie@localhost:3301
```

Для проверки получите кортеж, который был добавлен в спейс уже после полного резервного копирования:
```lua
crud.get('customers', 4)
```

В выводе появится запись `Alice Anderson`. Она добавлена после полного резервного копирования и есть только
в инкрементальном архиве. Наличие этого кортежа подтверждает, что восстановление применило
полный и инкрементальный архивы цепочки.

## Что выполняют скрипты-оркестраторы

Скрипты из директории `scripts/` выполняют роль оркестратора из архитектуры PITR. Они
автоматизируют рутинные действия, но не скрывают команды `tt`. Один и тот же `backup-id`
передаётся всем командам, аргументы подставляются из `plan.json`, а команды запускаются
на нужных узлах. Ниже описано, что делает каждый скрипт.

### backup.sh: резервное копирование

Скрипт принимает режим `full` (полное резервное копирование) или `incremental` (инкрементальное резервное копирование) и выполняет следующие шаги:

1. **Идентификатор бэкапа.** Все команды и файлы резервной копии связывает единый идентификатор `backup-id`.  Скрипт получает его командой ниже:

   ```shell
   tt backup-id
   ```

2. **План бэкапа.** На менеджере команда строит план резервного копирования и записывает его в файл `plan.json`
в контейнере `manager`:

   ```shell
   tt backup plan \
     --target=full \
     --backup-storage file:///backup/storage \
     -c http://etcd1:2379/tdb \
     -u admin -p secret-cluster-cookie \
     --format json > /backup/plan.json
   ```

   В плане в поле `master_instance_name` указан мастер-узел для каждого набора реплик. Для
инкрементального бэкапа план дополнительно содержит поле `from_vclock`, задающее
точку, с которой снимается дельта.

   План включает все наборы реплик кластера, в том числе роутер `router-1`, поэтому резервная копия
создается и для него: архив роутера и его запись в манифесте попадают в хранилище. На
восстановлении роутер не используется — см. раздел [«Восстановление на момент времени»](#восстановление-на-момент-времени).

3. **Снятие резервной копии с узлов.** Скрипт обходит мастер-узлы из плана и для каждого
запускает команду `tt backup start` в его контейнере. Имя экземпляра из плана (`storage-1-msk`)
скрипт превращает в имя сервиса `tarantool-storage-1-msk`:

   ```shell
   tt backup start \
     admin:secret-cluster-cookie@tarantool-storage-1-msk:3301 \
     --backup-id <backup-id> \
     --dir /backup/archives \
     --from-vclock '<from_vclock из плана>'
   ```

   Параметр `--from-vclock` используется только для инкрементального резервного копировании.
   При создании полной резервной копии этот параметр пропускается.

4. **Загрузка в хранилище.** На менеджере команда `tt backup upload` собирает
манифест и переносит архивы в хранилище. Списки `--archives` и `--fragments` скрипт
строит по UUID наборов реплик из `plan.json`. Файлы имеют имена
`<backup-id>-<uuid>.tar.zst` и `<backup-id>-<uuid>.json` и лежат в `/backup/archives`:

   ```shell
   tt backup upload \
     --archives /backup/archives/<backup-id>-<uuid-1>.tar.zst,/backup/archives/<backup-id>-<uuid-2>.tar.zst,... \
     --fragments /backup/archives/<backup-id>-<uuid-1>.json,... \
     --plan /backup/plan.json \
     --backup-storage file:///backup/storage \
     --backup-id <backup-id>
   ```

5. **Завершение резервного копирования** На каждом мастер-узле команда `tt backup finalize` закрывает резервную копию и
удаляет локальные архивы с узла:

   ```shell
     tt backup finalize \
     admin:secret-cluster-cookie@tarantool-storage-1-msk:3301 \
     --backup-id <backup-id> \
     --dir /backup/archives
   ```

### restore.sh: восстановление

Скрипт принимает параметр `target-time` (время точки восстановления) и выполняет следующие шаги:

1. **План восстановления.** На менеджере команда `tt restore plan` скачивает цепочку
архивов в каталог `/backup/restore` и записывает их в файл `plan.json`:

   ```shell
   tt restore plan \
     --target-time '<target-time>' \
     --backup-storage file:///backup/storage \
     -c http://etcd1:2379/tdb \
     --replicasets storage-1,storage-2 \
     -d /backup/restore \
     --format json > /backup/restore/plan.json
   ```

   Значение `--replicasets storage-1,storage-2` указывает хранилища с данными. Роутер в
   восстановление не входит (см. [«Восстановление на момент времени»](#восстановление-на-момент-времени)).

2. **Остановка хранилищ.** Команда `docker compose stop` останавливает все шесть
узлов хранилищ: `storage-1-msk`, `storage-1-spb`, `storage-1-brn`, `storage-2-msk`,
`storage-2-spb` и `storage-2-brn`.

3. **Подготовка каталогов данных.** Для каждого мастер-узла на менеджере выполняется
команда `tt restore apply`. Имя мастер-узла и UUID набора реплик скрипт получает из поля
`restore_targets` плана (ключ — UUID набора реплик, `instance_name` — имя мастера).
   Скрипт подставляет аргументы из плана:

   * `--archives` получен из `download_plan[<uuid>]`. Это цепочка архивов набора реплик в
  порядке «полный, затем инкрементальный»;
   * `--target-point` — из `recovery_point.trim_to_by_replicaset[<uuid>]`. Это позиция
  обрезки хвоста WAL;
   * `--work-dir` указывает каталог данных экземпляра, смонтированный в `manager`.

   ```shell
   tt restore apply \
     --archives /backup/restore/<backup-id-full>-<uuid>.tar.zst,/backup/restore/<backup-id-incr>-<uuid>.tar.zst \
     --work-dir /data/storage-1-msk \
     --target-point '<trim_to_by_replicaset из плана>'
   ```

4. **Очистка реплик.** Скрипт очищает каталоги данных реплик командами
`rm -rf /data/storage-1-spb/*`, `/data/storage-1-brn/*`, `/data/storage-2-spb/*` и
`/data/storage-2-brn/*`. Реплики пересоздаются с нуля и при старте догоняют мастер-узел.

5. **Запуск хранилищ.** Команда `docker compose start` снова запускает хранилища.
   Кластер поднимается с восстановленными данными.

## Остановка стенда

Остановите стенд и удалите его данные:

```shell
make stop
```
