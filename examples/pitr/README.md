# Резервное копирование и восстановление на момент времени (PITR)

В этом руководстве показано, как выполнить резервное копирование кластера Tarantool DB
и восстановить его данные на заданный момент времени (point-in-time recovery, PITR)
с помощью утилиты [tt CLI](https://www.tarantool.io/docs/tdb/ru/3_x/install_and_upgrade/install_tt).

Резервное копирование и восстановление является кластерной операцией. Утилита `tt` выполняет
её на узлах Tarantool и на отдельном хосте-менеджере, а файлы между ними переносит оркестратор.
В примере роль оркестратора выполняют скрипты `scripts/backup.sh` и `scripts/restore.sh`,
которые запускаются целями `make`.

## Запуск стенда

Для успешного запуска должны быть свободны следующие порты:

* 2379
* 3301–3307

Перейдите в директорию примера `pitr`:

```shell
cd examples/pitr
```

Запустите стенд:

```shell
make start
```

Команда последовательно выполняет следующие шаги:
1. Запускает централизованное хранилище конфигурации — кластер etcd;
2. Загружает конфигурацию кластера в централизованное хранилище;
3. Запускает кластер Tarantool DB. Контейнер `init_host` в его составе загружает
   миграции в кластер и выполняет их.

Запущенный стенд состоит из:

* кластера Tarantool DB:
  * роутера `router-1` (порт `3301`);
  * двух наборов реплик по три хранилища в каждом:
    * `storage-1`: мастер `storage-1-msk` (порт `3302`), реплики `storage-1-spb` (порт `3303`) и `storage-1-brn` (порт `3304`);
    * `storage-2`: мастер `storage-2-msk` (порт `3305`), реплики `storage-2-spb` (порт `3306`) и `storage-2-brn` (порт `3307`);
  * контейнера `manager` (хоста-менеджера резервного копирования);
* кластера etcd из 3 узлов.

После запуска должны работать все контейнеры, кроме [init_host](../up_with_docker_compose/README.md#контейнер-init_host).

При запуске миграция создаёт шардированный спейс `customers` с полями `id`, `bucket_id`,
`name`, `surname` и `age`.

На роутере включена роль `roles.recovery-point-manager`, которая каждые 30 секунд
автоматически создаёт кластерную точку восстановления на всех мастерах хранилищ.
Подробнее о роли и точках восстановления см. в разделе
[«Как устроено резервное копирование и восстановление»](#как-устроено-резервное-копирование-и-восстановление).

## Используемые файлы

В руководстве используются следующие файлы примера `pitr`:

* `cluster/` — директория c файлами для запуска кластера Tarantool DB:
  * `config.yml` — конфигурация и топология кластера, включая роль
    `roles.recovery-point-manager` на роутере;
  * `docker-compose.yml` — описание узлов кластера Tarantool DB и контейнера `manager`;
  * `migrations/scenario` — директория, содержащая файлы с описанием миграций;
* `tools/docker-compose.yml` — описание кластера etcd из 3 узлов, который хранит конфигурацию кластера;
* `scripts/` — директория со скриптами-оркестраторами:
  * `backup.sh` — полное и инкрементальное резервное копирование;
  * `restore.sh` — восстановление на момент времени;
* `Makefile` — цели для запуска и остановки стенда, резервного копирования и восстановления.

## Как устроено резервное копирование и восстановление

Утилита `tt` выполняет резервное копирование и восстановление в двух ролях:

* на **узле Tarantool** она создаёт локальный архив данных командой `tt backup start`,
  финализирует бэкап командой `tt backup finalize`, а при восстановлении подготавливает
  каталог данных командой `tt restore apply`;
* на **хосте-менеджере** (отдельной машине с `tt`) она строит план командой
  `tt backup plan`, собирает манифест и заливает архивы в хранилище командой
  `tt backup upload`, а при восстановлении скачивает цепочку архивов и строит план
  командой `tt restore plan`.

Файлы между узлами и менеджером переносит **оркестратор** (внешняя система: ATE, скрипты
или CI/CD). В примере эту роль выполняют скрипты из директории `scripts/`.

В примере файлы размещены так:

* **Резервные копии** — в хранилище `/backup/storage` (именованный том `backup`), на
  которое указывает флаг `--backup-storage`. С хранилищем работает только менеджер.
* **Локальные архивы** — промежуточные файлы на мастер-узлах, в каталоге
  `/backup/archives` (тот же том `backup`). Том смонтирован и в `manager`, и в
  мастер-узлы хранилищ, поэтому менеджер видит архивы напрямую и переносить их
  не нужно.
* **Данные инстансов** — снапшоты и WAL Tarantool, в именованных томах `*-data`,
  смонтированных в `manager` под путями `/data/<инстанс>`.

> [!NOTE]
> Общие тома — упрощение для примера. В продакшене узлы и менеджер — это отдельные
> машины, и локальные архивы между ними переносятся по SSH, а данные инстансов
> находятся на самих узлах. Точно так же `--backup-storage` указывает здесь на файловое
> хранилище (`file:///backup/storage`), чтобы не поднимать отдельный сервис. В продакшене
> резервные копии обычно хранят в S3-совместимом объектном хранилище, которое `tt` тоже
> поддерживает: короткой формой `s3://<bucket>/<prefix>` с учётными данными из переменных
> окружения `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY` либо полной формой `@config.yaml`
> с полями `type`, `endpoint`, `region`, `bucket`, `prefix`, `access_key_id` и
> `secret_access_key` для кастомного endpoint и региона.

В примере выполняется два бэкапа одной цепочки: полный, затем инкрементальный.
Восстановление выполняется на момент времени точки восстановления `before-incr`.

### Точки восстановления

Восстановление на момент времени выполняется по точкам восстановления (recovery
points) — меткам в WAL с отметкой времени. Их создаёт роль
`roles.recovery-point-manager`, включённая на роутере.

## Запись данных

Команда `tt connect` открывает интерактивную консоль Tarantool. Подключитесь к роутеру
(порт `3301`) и запишите данные в спейс `customers`:

```shell
tt connect admin:secret-cluster-cookie@localhost:3301
```

```lua
crud.insert_many('customers', {
    {1, box.NULL, 'Elizabeth', 'Bagnall', 12},
    {2, box.NULL, 'Mary', 'Bowman', 46},
    {3, box.NULL, 'David', 'Bradley', 33},
    {1001, box.NULL, 'William', 'Bridgens', 81},
    {1002, box.NULL, 'Jack', 'Brown', 35},
    {1003, box.NULL, 'William', 'Long', 25},
})
```

Значение `box.NULL` вместо `bucket_id` означает, что `bucket_id` вычисляется
автоматически. Для выхода из консоли нажмите `CTRL+D`.

## Полное резервное копирование

Точки восстановления создаются ролью `roles.recovery-point-manager` автоматически,
поэтому перед полным бэкапом вручную ничего создавать не нужно.

### Бэкап

Выполните полный бэкап:

```shell
make backup-full
```

Скрипт `scripts/backup.sh` выполняет пять шагов: получает идентификатор командой
`tt backup-id`, строит план командой `tt backup plan`, снимает бэкап с каждого мастера
командой `tt backup start`, загружает архивы командой `tt backup upload` и финализирует
бэкап командой `tt backup finalize`. Каждый шаг скрипт выводит в консоль. Подробнее
смотрите в разделе [«Что выполняют скрипты-оркестраторы»](#что-выполняют-скрипты-оркестраторы).

## Инкрементальное резервное копирование

Запишите ещё данные в спейс `customers`:

```shell
tt connect admin:secret-cluster-cookie@localhost:3301
```

```lua
crud.insert_many('customers', {
    {4, box.NULL, 'Alice', 'Anderson', 28},
    {5, box.NULL, 'Robert', 'Campbell', 41},
    {1004, box.NULL, 'Sarah', 'Mitchell', 33},
    {1005, box.NULL, 'James', 'Carter', 55},
})
```

### Точка восстановления before-incr

Перед инкрементальным бэкапом создайте точку восстановления с меткой `before-incr`.
Команда на роутере (порт `3301`) записывает метку на мастер каждого набора реплик:

```shell
tt connect admin:secret-cluster-cookie@localhost:3301
```

```lua
vshard.router.create_cluster_recovery_point('before-incr')
```

В ответе команда возвращает по метке на каждый набор реплик с полем `timestamp` (время
в секундах, с дробной частью). Для восстановления нужна его целая часть. Например, из
`1790799106.5178132` это `1790799106`. Значения у наборов реплик почти совпадают,
подойдёт любое.

### Бэкап

Выполните инкрементальный бэкап:

```shell
make backup-incremental
```

## Повреждение данных

Чтобы имитировать потерю данных, очистите спейс `customers` через `crud` на роутере
(порт `3301`):

```shell
tt connect admin:secret-cluster-cookie@localhost:3301
```

```lua
crud.truncate('customers')
```

## Восстановление на момент времени

Восстановите данные к точке `before-incr`, то есть к моменту, когда были записаны обе
порции данных. Передайте в переменной `TARGET_TIME` целую часть поля `timestamp` этой
точки:

```shell
make restore TARGET_TIME='1790799106'
```

Вместо `1790799106` подставьте целую часть `timestamp`, полученную при создании точки
`before-incr`.

Скрипт `scripts/restore.sh` выполняет пять шагов. Он строит план восстановления командой
`tt restore plan`, останавливает хранилища, подготавливает каталоги данных командой
`tt restore apply` на каждом мастере, очищает каталоги реплик и запускает хранилища.

Восстанавливаются только мастер-узлы хранилищ, на те же инстансы, с которых снимался
бэкап. Реплики не восстанавливаются из бэкапа: их каталоги данных очищаются, и при старте
они заново догоняют мастер. Роутер не хранит данные и стартует с пустого состояния, хотя
в бэкап он входит (см. [«backup.sh: резервное копирование»](#backupsh-резервное-копирование)).

Подменять идентификаторы экземпляров (`--patch-uuid`) не нужно. Мастер восстанавливается
на себя, поэтому `instance_uuid` в архиве уже совпадает с текущим. Флаг требуется только
при переносе бэкапа на другой инстанс — например, при поднятии потерянного узла заново
как нового.

После восстановления проверьте данные на роутере (порт `3301`):

```shell
tt connect admin:secret-cluster-cookie@localhost:3301
```

```lua
crud.get('customers', 4)
```

В выводе появится запись `Alice Anderson`. Она добавлена после полного бэкапа и есть только
в инкрементальном архиве, поэтому её наличие подтверждает, что восстановление применило
полный и инкрементальный архивы цепочки.

## Что выполняют скрипты-оркестраторы

Скрипты из директории `scripts/` выполняют роль оркестратора из архитектуры PITR. Они
автоматизируют рутинные действия, но не скрывают команды `tt`. Один и тот же `backup-id`
передаётся всем командам, аргументы подставляются из `plan.json`, а команды запускаются
на нужных узлах. Ниже описано, что делает каждый скрипт.

### backup.sh: резервное копирование

Скрипт принимает режим `full` или `incremental` и выполняет пять шагов.

**Шаг 1. Идентификатор бэкапа.** Один `backup-id` связывает все команды и файлы одного
бэкапа. Скрипт получает его командой:

```shell
tt backup-id
```

**Шаг 2. План бэкапа.** На менеджере команда строит план и пишет его в файл `plan.json`
в контейнере `manager`:

```shell
tt backup plan \
  --target=full \
  --backup-storage file:///backup/storage \
  -c http://etcd1:2379/tdb \
  -u admin -p secret-cluster-cookie \
  --format json > /backup/plan.json
```

В плане для каждого набора реплик указан мастер (поле `master_instance_name`). Для
инкрементального бэкапа план дополнительно содержит поле `from_vclock`, которое задаёт
точку, с которой снимается дельта.

План включает все наборы реплик кластера, в том числе роутер `router-1`, поэтому бэкап
снимается и с него: его архив и запись в манифесте попадают в хранилище. На
восстановлении роутер не используется — см. [«Восстановление на момент времени»](#восстановление-на-момент-времени).

**Шаг 3. Снятие бэкапа с узлов.** Скрипт обходит мастеров из плана и для каждого
вызывает `tt backup start` в его контейнере. Имя инстанса из плана (`storage-1-msk`)
скрипт превращает в имя сервиса `tarantool-storage-1-msk`:

```shell
tt backup start \
  admin:secret-cluster-cookie@tarantool-storage-1-msk:3301 \
  --backup-id <backup-id> \
  --dir /backup/archives \
  --from-vclock '<from_vclock из плана>'
```

Флаг `--from-vclock` передаётся только для инкрементального бэкапа. Для полного бэкапа
он опускается.

**Шаг 4. Загрузка в хранилище.** На менеджере команда `tt backup upload` собирает
манифест и переносит архивы в хранилище. Списки `--archives` и `--fragments` скрипт
строит по UUID наборов реплик из `plan.json`. Файлы имеют имена
`<backup-id>-<uuid>.tar.zst` и `<backup-id>-<uuid>.json` и лежат в `/backup/archives`:

```shell
tt backup upload \
  --archives /backup/archives/<backup-id>-<uuid-1>.tar.zst,/backup/archives/<backup-id>-<uuid-2>.tar.zst,... \
  --fragments /backup/archives/<backup-id>-<uuid-1>.json,... \
  --plan /backup/plan.json \
  --backup-storage file:///backup/storage \
  --backup-id <backup-id>
```

**Шаг 5. Финализация.** На каждом мастере команда `tt backup finalize` закрывает бэкап и
удаляет локальные архивы с узла:

```shell
tt backup finalize \
  admin:secret-cluster-cookie@tarantool-storage-1-msk:3301 \
  --backup-id <backup-id> \
  --dir /backup/archives
```

### restore.sh: восстановление

Скрипт принимает `target-time` (время точки восстановления) и выполняет пять
шагов.

**Шаг 1. План восстановления.** На менеджере команда `tt restore plan` скачивает цепочку
архивов в каталог `/backup/restore` и пишет `plan.json`:

```shell
tt restore plan \
  --target-time '<target-time>' \
  --backup-storage file:///backup/storage \
  -c http://etcd1:2379/tdb \
  --replicasets storage-1,storage-2 \
  -d /backup/restore \
  --format json > /backup/restore/plan.json
```

Значение `--replicasets storage-1,storage-2` указывает хранилища с данными. Роутер в
восстановление не входит (см. [«Восстановление на момент времени»](#восстановление-на-момент-времени)).

**Шаг 2. Остановка хранилищ.** Команда `docker compose stop` останавливает все шесть
узлов хранилищ: `storage-1-msk`, `storage-1-spb`, `storage-1-brn`, `storage-2-msk`,
`storage-2-spb` и `storage-2-brn`.

**Шаг 3. Подготовка каталогов данных.** Для каждого мастера на менеджере выполняется
команда `tt restore apply`. Имя мастер-узла и UUID набора реплик скрипт берёт из поля
`restore_targets` плана (ключ — UUID набора реплик, `instance_name` — имя мастера).
Аргументы подставляются из плана:

* `--archives` берётся из `download_plan[<uuid>]`. Это цепочка архивов набора реплик в
  порядке «полный, затем инкрементальный»;
* `--target-point` берётся из `recovery_point.trim_to_by_replicaset[<uuid>]`. Это позиция
  обрезки хвоста WAL;
* `--work-dir` указывает каталог данных инстанса, смонтированный в `manager`.

```shell
tt restore apply \
  --archives /backup/restore/<backup-id-full>-<uuid>.tar.zst,/backup/restore/<backup-id-incr>-<uuid>.tar.zst \
  --work-dir /data/storage-1-msk \
  --target-point '<trim_to_by_replicaset из плана>'
```

**Шаг 4. Очистка реплик.** Скрипт очищает каталоги данных реплик командами
`rm -rf /data/storage-1-spb/*`, `/data/storage-1-brn/*`, `/data/storage-2-spb/*` и
`/data/storage-2-brn/*`. Реплики пересоздаются с нуля и при старте догоняют мастер.

**Шаг 5. Запуск хранилищ.** Команда `docker compose start` снова запускает хранилища.
Кластер поднимается с восстановленными данными.

## Остановка стенда

Остановите стенд и удалите его данные:

```shell
make stop
```
